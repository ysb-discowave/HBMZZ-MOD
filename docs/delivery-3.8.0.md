## 二、3.8.0 交付内容

### 1. 视频大屏（重做）

- 方块 `hbmzz:video_screen`：控制器格有方块实体，其余格是同一方块 `part=true` 的填充格，
  **填充格没有方块实体**——画面只可能被画一次，不会出现「十二个控制器各画一遍」或「谁都以为别人画了」。
- 朝向与镜像一次算清，全部取自 `dfc/ConsoleRig`：
  - `anchor(cols, rows, facing)`：控制器是墙的左上格，面板中心要按列 / 行推过去；
  - `yawOf(facing)`：把渲染器局部 `-z` 转到方块朝向；
  - `panelUv()`：u 反向（玩家站在正面时局部 +x 是他的左手），图像左边缘才落在观看者左手边。
  三处各自为政就是「北面正常、东西镜像、上下颠倒」的来源；现在四个朝向一致。
- 画面用 `PanelPainter.glass` 画一张带 UV 的四边形，位置在方块表面外 0.002 格，不与方块模型 z-fighting。
- 尺寸：1–32 格 × 1–32 格，从配置窗口调。变大补格、变小只收掉这面墙自己的格
  （`trimParts` 只清 `part=true` 的同方块格，不碰玩家放的东西）。
- 拆任意一格整面消失，只掉一个物品（`getDrops` 空表，掉落由拆除函数在被打的那格手动生成）。
  控制器方块实体已丢失时按列 / 行扫描兜底，不会留下孤儿格。

### 2. 大屏遥控器（新增）

- 物品 `hbmzz:video_remote`，16×16 手持机贴图（深灰机身、顶部信号窗、方向键、两枚按键），
  由 `tools/art/make_video_textures.py` 生成，可重跑。
- **普通物品，不是 `ItemBlock`**：不可放置、没有点击放置行为、也不会弹「不能放置」；
  右键别的方块返回 `PASS`，把点击让回去。
- 只做连接：右键播放器对准 → 右键大屏（点任一格）绑定。两者相距上限 64 格，玩家要够得着大屏（12 格内）。
- 绑定在服务端落地：写大屏的播放器坐标、片名、音量，写播放器的大屏坐标。

### 3. 播放器（视频广播器）与拉杆语义

- **站立右键 = 大屏展示**：对着播放器右键，接了大屏就把片子放到那块屏上、客户端进"展示模式"——
  画面是屏自己的解码器给的，声音也是那一路，窗口里没有进度条也没有第二份播放实例（详见第 12 节）。
  没有片源时开菜单让人先挑一个；接了屏但屏不在本机已加载区时，才退回本机全屏播放。
  **F 键切全屏**（`Minecraft.toggleFullscreen()`，再按一次回窗口），退出时把进入前的显示模式还回去。
- **蹲下右键 = 菜单**：原来那个"片名 + 选择器 + 打开文件夹 + 刷新列表"的窗口搬到蹲下；
  音量与「强制限制返回」不再单独占一个右键，改为这个窗口里的「播放器设置」按钮。
- 红石上升沿触发保持不变。
- **接上大屏之后**，红石只做开 / 停：上升沿让大屏开始播放，下降沿让它停；
  误触拉杆不会把任何人切进全屏。
- **没接大屏时**保持原逻辑：上升沿直接全屏接管，按「强制限制返回」（默认开启）决定能不能 ESC 中途退出。
- 大屏所在区块没加载时不会偷偷降级成全屏，只写一行状态；大屏被拆则自动解绑，拉杆回到原行为。
- 首次 tick 只「采纳」当前信号、不触发任何动作（登录在通电的拉杆旁边不会被突然接管）。

### 4. 音量与「强制限制返回」

- 从大屏搬到了播放器，入口是「蹲下右键播放器 → 播放器设置」：窗口里只有一条 0–200% 音量滑条
  与一个「强制限制返回」开关。它不再自己占一个右键，因为右键现在是"直接播放"。
- **默认开启**（`config/hbmzz.cfg` 的 `video.allowEsc` 只是新方块与旧存档缺字段时的种子值，
  默认 `false` 即限制开启）。开关是**每台播放器各自一份**，存在方块 NBT 里（键 `restrictBack`，
  旧存档的 `forceExit` 仍然读得懂）。
- **只在没接大屏时生效**：没接大屏，全屏接管期间按 ESC 只提示、不退出；接上大屏后立刻不生效，
  退出归大屏与拉杆，画面上连相关提示都不再出现；大屏被拆掉则自动恢复限制。
- **同步是"每次现问"而不是"打开时记一份"**：`GuiVideoScreen` 每次判键、每 tick 都回查这台播放器的
  方块实体（`hasScreen()`），所以遥控器中途接上大屏、或者大屏被拆，下一次按键就是新结论。
  方块实体不在已加载区时沿用上一次的结论（"看不见"不等于"被拆了"）；方块本身没了则按没接大屏处理。
- **播放界面里没有任何按钮或入口**：`GuiVideoScreen` 不建 `buttonList`，regcheck #67 守着这一条。
  能改它的只有这个设置窗口；窗口里同时直接写出当前状态（"当前已接大屏 · 本项不生效" /
  "当前未接大屏 · 本项生效中"），不用去别处猜。
- 两项随广播包走（片名 + 音量 + 限制开关 + 播放器坐标），全屏与大屏两条路径用同一套设置；
  坐标是给客户端回查连接状态用的（regcheck #69 守着报文里那一格）。
- 滑条是自绘的（`GuiVideoPlayerConfig`）：0.5 基线 × 百分比，100% = 默认音量，200% 才真的更响
  （音频层在 1.0 处夹紧；基线若设成 0.65，滑条后半段会没有反应）。

### 5. 视频目录：运行中换片

- 广播器窗口新增「打开视频文件夹」（`Desktop.open`，失败时把路径写进状态行）与「刷新列表」。
- 刷新现在会**说出被跳过的文件**：目录里不是 `.zip` 也不是子目录的东西（典型是一个 `.mp4`）
  会进 `VideoLibrary.skipped()`，窗口与 F7 的回执都写明"跳过 1 个不支持的文件：xxx.mp4（需打包成 zip）"。
  `config/hbmzz/videos/README.txt` 也补了同一句话。
- 新增刷新键 **F7**（`key.hbmzz.video_refresh`）：`VideoLibrary.rescan()` 清掉一秒列表缓存，并在物品栏上方报数量。
  没用 F3+T —— 那是原版重载资源包，按一次会重新烘焙所有模型。

### 6. 回退到仓库原实现，音乐回原版

- 撤回上一版的替代实现：`VideoClip` 的「文件集 + 时间线 / playlist / desc.txt / pingpong」、
  悬浮观看窗、多屏共用解码、旧的 `VideoScreenPlayback` 全部移除；
  `VideoClip` / `VideoPlayer` / `VideoAudio` / `VideoLibrary` / `GuiVideoScreen` / `ItemMonitorLinker`
  一律还原为仓库版本，视频仍按「文件名 + fps + 帧号」读取。
- 数据线（`monitor_linker`）不再参与接大屏，回到仪表 / 堆芯 / 摄像头。
- 音乐回到仓库原版：片头恢复**静音**（192 帧 / 24 fps / 8.0000 s，无 `audio` 字段），
  片尾仍是仓库自带的 `the-ending-of-melting.mp3`（2326 帧 / 12 fps / 193.8333 s，带 `audio.wav`）。
  自制配乐与英文口播的脚本（`tools/audio/ost_synth.py`、`voice_over.py`）与成片全部移除。

### 7. 播放定位与同步（本批新增）

- **右键大屏**打开 `GuiVideoSeek`：可拖动的进度条、`-30s` / `-5s` / `+5s` / `+30s`、
  「回开头（重新播放）」、「暂停 / 继续」。蹲下右键仍是尺寸 / 倍速窗口，两个问题分开问。
- 播放头是**方块上的状态**，不是窗口里的变量：`TileEntityVideoScreen` 存
  `progressMs`（基准毫秒）+ `anchorTick`（世界 tick）+ `paused`，
  `positionMs()` = 基准 + 走过 tick × 50ms × 倍速；暂停、停止时基准就是最终位置。
- **一次定位走一条路**：窗口 → `VideoSeekMessage`（id 27）→ 服务端 → 改方块 → `notifyBlockUpdate`
  → 范围内所有客户端重算位置。按键的人、旁边的人、服务器另一头的人落到同一帧；
  **单机就是集成服务端跑同一段代码**，两种模式不存在第二条实现。
- 时间边界**两层夹**：服务端只接受 `0..MAX_PROGRESS_MS`（6 小时）；客户端再用本机那份片子的
  `durationSeconds()` 夹一次。「-5 秒」不会变成负数，片尾之后也不会因为「目标越界」反复重定位。
- 暂停是第三种状态，不复用拉杆：`playing` 归拉杆，`paused` 只是把时钟按住——
  画面定在当帧、解码器不释放、音轨停在同一位置，继续时从原位接上，不会从头开始。
- **停止 = 回开头**：`setPlaying(false)` 把进度清零并解暂停，与「红石一路一次播放」的原意一致；
  换片（`setVideo` 名字变化）同样回开头。`applySpeed` 先按旧倍速折算进度再改倍速，调倍速不会跳帧。
- 客户端 `VideoScreenPlayback` 每帧把本机播放器往方块的时间轴对齐，偏差 > 0.35 秒才 `seekTo`；
  暂停期间不动。`VideoPlayer` 的时钟改成「基准时间 + 走时」，`seekTo` 让解码线程跳到目标帧
  （解码线程不再在片尾退出，可回退重新解码），音轨一起跳。
- 运行中刷新：窗口里的时间与状态每帧从方块读，墙上画面由同一条对齐链路跟上，没有额外的定时同步包。

### 9. 「刷新无效 / 装进去不生效」的排查结论（本批新增）

- **证据**：这台机器的 `config/hbmzz/videos/` 里躺着 `Video_1781791115891_250.mp4`（2.0 MB），
  另有 `hbmzz-intro.zip`、`hbmzz-credits.zip`。`latest.log` 里 `hbmzz@3.8.0` 正常加载
  （"Client attempting to join with 22 mods ... hbmzz@3.8.0"），所以**不是模组没装进去**。
- **原因**：视频库只认 `<名字>.zip` 和 `<名字>/` 两种形状（`VideoLibrary.names()` 的过滤条件），
  `.mp4` 被静默忽略。列表永远只有那两个 zip，于是"按了刷新没变化"看起来像按钮坏了；
  把 mp4"装进去"也当然不生效——这个模组读的是图片帧序列，1.12.2 的 JRE 没有 H.264 解码器。
- **修复**：库记账（`skipped()`），窗口与 F7 把被跳过的文件名念出来并给出做法（`tools/video/pack.py`
  转成 zip）；README 同步说明。**没有**假装支持 mp4——那需要一个每平台各带一份的本地解码库。
- **验证**：用模组自己的 `VideoLibrary` 在真实目录上跑了一遍：`clips = [hbmzz-credits, hbmzz-intro]`、
  `skipped = [Video_1781791115891_250.mp4]`、`exists("hbmzz-intro") = true`。
- **"装进去不生效"的第二种可能**（游戏读的不是刚换的 jar）现在会自己说出来：
  preInit 打一行 `HBMZZ 3.8.0 loaded from <jar 路径>`，重启后先看这行指向哪个文件。

### 10. FFmpeg 自动下载：确认已丢失，按上一版恢复（本批新增）

- **核对结论：逻辑不在了。** 当前源码的 `BundledFfmpeg` 只剩"把 jar 内 `/assets/rsaudiofm/ffmpeg.exe`
  释放出来"，而两种包里都没有这个资源（`unzip -l` 查过），于是候选 0 每次都是 null，日志只剩
  一句"未找到可用的 ffmpeg"。上一版的下载器只留在 `backupsmod/hbmzz-old-jars/hbmzz-3.7.0.jar.bak` 里：
  `BundledFfmpeg` 17 KB（带 `$HeadInfo` / `$Progress`）与 `GuiFfmpegDownload`。源码回到 3.7.1 基线时，
  这两个文件跟着没了。
- **恢复的东西**（据 3.7.0 的源码 `_srcpkg/370` 原样搬回，只补了一处并发保护）：
  - `BundledFfmpeg`：在线下载 BtbN 的 `ffmpeg-master-latest-win64-gpl.zip`，走
    `https://yxz.ysbdwz.dpdns.org/download?url=` 代理；HEAD 拿总长与 `Accept-Ranges`，支持就切 64 段
    并行（每段一个 `.seg` + `.done` 标记，断了下次只补没下完的段），不支持退回单线程；合并后校验总长，
    再流式解压出 `bin/ffmpeg.exe`；落到 `config/rsaudiofm/bin/`，同目录 `.stamp` 记住源 URL，命中就复用。
    代理与源可被 `-Drsaudiofm.ffmpeg.proxy` / `-Drsaudiofm.ffmpeg.source` 覆盖。
  - `GuiFfmpegDownload`：进世界前的进度页。后台线程跑 `ensure()`，主线程每帧只读 `progress()` 画条，
    ESC 期间不响应，完成/失败都自动关闭并回调。
  - `FormatsBootstrap.onClientTick` 第一次 tick：`setGameHint` 之后先问 `BundledFfmpeg.isReady(mc.mcDataDir)`；
    没有就打开进度页，回调里 `FfmpegFinder.reset() + ConvertQueue.scanAndEnqueue()`（这样刚下好的 exe
    立刻被识别）；有就直接 reset + 扫描。
- **补的一处并发保护**：`ensure()` 用 `AtomicBoolean` 保证同一时刻只有一次下载。播放线程在下载中途问
  `FfmpegFinder.path()` 时不再跟着下一遍（那会和进度页往同一批分片里写，拼出来的 zip 是坏的），
  而是立刻拿 null 走外置候选，本次播放按"没有 ffmpeg"降级，下载完自动恢复。
- **实跑验证**（本地假代理 + 假 zip，结构同 BtbN 包：`<root>/bin/ffmpeg.exe`）：
  - 分段模式：1 个 HEAD + 64 个 206 Range 请求，1.4 s 完成，解出 1,048,576 字节，
    `.stamp` 写入 `src=...`，`isReady` 由 false 变 true，下载目录只剩 `ffmpeg.exe` + `.stamp`（分片与 zip 全部清理）。
  - 不支持 Range 的服务端：自动退回单线程，72 ms 同样成功，结果一致。
- **首次启动的表现**：主菜单阶段弹出"正在准备音频播放器"进度页（约 190 MB），下完自动关闭，之后不再重复下载。
  已有匹配 stamp 的本地副本时直接跳过这一步。

### 11. 视频格式全支持：把"播放"换成"导入"（本批新增）

- **结论先行：播放端一个解码器都没加。** 1.12.2 的 JRE 只有一套，塞 H.264/HEVC/AV1 解码
  意味着每个平台各带一份二进制，还得跟着显卡驱动走。所以"支持市面上所有格式"落在导入这一步：
  用 ffmpeg 把任何容器拆成图片帧 + PCM 音轨，再按 `VideoClip` 认识的形状打包。ffmpeg 认多少
  格式，这里就能导多少格式，而模组自己仍然只做 `ImageIO` 能做的事。
- **新增 `VideoFormats`**：认得 mp4 / m4v / mov / 3gp / mkv / webm / avi / wmv / asf / flv /
  ts / m2ts / mts / mpg / mpeg / vob / rm / rmvb / ogv / mxf 等容器，外加 mp3 / flac / wav /
  aac / opus 这类纯音频（导进来只有声音，界面上明说）。列表以外的文件仍旧按"不支持"提示，
  不会静默消失。
- **新增 `VideoImportQueue`**：单线程守护队列，一次一集。
  - 探测时长（`ffmpeg -i` 的 `Duration:` 行）→ 估总帧数 → 每 400 ms 数一次临时目录里的 jpg
    来推进度条；真实帧数解完再数一遍写进 `meta.json`。
  - 命令：`-vf fps=F,scale=W:-2:flags=lanczos -q:v 4`，音轨单独一遍
    `-vn -ac 2 -ar 44100 -c:a pcm_s16le`（没有音轨就跳过，不留空文件）。
  - 打包用 STORED（jpg 本来就压过），产物 `<名字>.zip` 直接落进 `config/hbmzz/videos/`，
    撞名自动加 `_2`；临时目录 `.import/` 转完即清。
  - 关窗口不打断转换；重新打开还能看到进度。取消会 `destroy()` 当前 ffmpeg 并清空队列。
- **名字放开到各语言字母**：`VideoLibrary.isValidName` 以前只收 ASCII，中文片名转出来的包只能叫
  `video`。现在按 `Character.isLetterOrDigit` 判，中文名原样保留；分隔符、空格、控制字符、
  首字符非字母数字、末尾点号仍然一律拒绝——没有 `/` 和 `\` 就没有目录穿越，这条没松。
- **两处入口**：蹲下右键播放器的窗口多了「导入视频…」按钮；刷新/F7 的回执把"待导入 N 个视频"
  和"跳过 N 个不支持的文件"分开说（mp4 不再算坏文件）。
- **实跑验证（真 ffmpeg + 模组自己的类）**：
  - 3 秒测试片（640×360 / 30 fps / AAC）→ 10 fps、480 宽：30 帧、3.00 秒、`audio.wav` 529,278 字节、
    包名 `测试片段.zip`、`VideoClip` 读回首帧与末帧都成功。
  - 目录里那个真片 `Video_1781791115891_250.mp4`（104.43 秒 / 854×426 / AV1）→ 10 fps、480 宽：
    **1044 帧、104.40 秒、25 MB zip，几秒内转完**，首末帧解码成功；进度条 30% → 69% → 打包。
  - 包内结构核对：`meta.json`（fps/frames/title/audio）+ `f000001.jpg…` + `audio.wav`，与手打包一致。

### 12. 右键识别与大屏展示、单音源（本批新增）

**一、右键"识别不到"的真因**（`PlayerControllerMP.processRightClickBlock` / `PlayerInteractionManager` 同一个判据）：

```java
if (!player.isSneaking() || bypass || event.getUseBlock() == ALLOW)
    block.onBlockActivated(...)
```

空手的 `ItemStack.doesSneakBypassUse` 返回 true，所以"蹲下右键空手"能开窗口；手里拿着**任何**东西
（镐子、方块、食物）这个判断就为假，方块**根本没被调用**。这就是"有时候点了没反应"——不是窗口坏了，
是那次点击没到方块。修法不是改方块，而是在 `RightClickBlock` 事件里对这两块方块回 `ALLOW`
（`common/VideoClickHandler`，客户端与服务端同一份，因为服务端也会再判一次）；作用范围只限这两块，
不动"潜行 = 用手里的东西"这条原版规矩。顺手把遥控器让位那一条也收窄成"只有站着的点击才让"。

**二、站立右键改成"大屏展示"**：以前右键开的是 `GuiVideoScreen` 的全屏播放器（带进度条、自己的解码器
和音轨），于是世界里的屏还在放、窗口里又放一份。现在：

- 接了屏且屏在本机已加载区 → `GuiVideoScreen.mirror()`：窗口每帧向那块屏的 `VideoScreenPlayback`
  要帧，自己不持有播放实例，也不画进度条（进度归"右键大屏"的定位窗口）。退出只放下指针，不关屏的解码器。
- 服务端在同一个右键里调 `TileEntityVideoBroadcaster.startDisplay()`：把片源/音量推给屏并 `setPlaying(true)`。
  拉杆仍然是权威——下一次信号变化 `driveScreen()` 会把屏重新对齐到红石状态。
- 没接屏、或屏不在本机已加载区（那边没有屏在发声）→ 才退回本机全屏播放。
- 客户端拿不到方块实体时（刚放下 / 刚重连）开的是菜单，不再是一次空点击。

**三、单音源**（`client/video/VideoAudioPolicy`，每 client tick 判一次）：

| 当前界面 | 谁发声 |
| --- | --- |
| 任何设置类窗口（广播器 / 播放器设置 / 导入 / 大屏配置 / 定位 / 暂停菜单） | 没有人 |
| 全屏接管（广播） | 只有它自己的解码器；世界里所有大屏静音 |
| 大屏展示（mirror） | 只有被展示的那块屏 |
| 没有窗口 | 只留**最近**的一块正在播的屏（64 格内），其余静音 |

- 静音 ≠ 暂停：`VideoAudio.apply()` 只在 `paused || muted` 时 `clip.stop()`，位置不动；恢复时
  `VideoPlayer.setMuted(false)` 会把音轨 `seek(filmSeconds())`，所以画面、屏的时钟一直走，恢复不落后。
- 一个房间里四块屏放同一部片子，以前是四份音轨错开几毫秒一起响；现在只有最近的那一块说话。
- 兜底：`GuiVideoScreen.reap()` 每 tick 检查"当前界面还是不是我"，换世界、被别的界面顶掉、
  某条路径漏了 `onGuiClosed`——三种情况都会把解码器关掉，不会留下一个没有窗口的声音。

### 13. 导入窗口居中与帧率 120（本批新增）

**一、"斜着、往旁边"的真因**：`GuiVideoImport` 的面板宽度是写死的 `W = 360`，位置按 `(width - 360) / 2` 算。
GUI 缩放大的一档下可用宽度只有 320，`left` 直接变负数——面板左边 40 px 被切在视口外，右边顶到边上，
看上去整块板子歪在右边。不是绘制的问题，是"面板比屏幕宽"这件事从来没被处理。

- 现在 `W = max(220, min(360, width - 16))`，`left = max(4, (width - W) / 2)`，`top` 同样夹住；
  窄窗口里面板变小，而不是被切掉。
- 按钮不再写死 x 坐标，按 `(面板宽 - 24 - 2*gap) / 3` 分三列，第三列吃掉余量；下面那条 ffmpeg 按钮横跨整幅。
- `updateScreen()` 比对上次排版的视口尺寸，变了就重排——拉窗口、改全屏、切 GUI 缩放都走这条路，
  以前只有 `initGui()` 会重排，按钮会留在旧位置上。

> **更正（批次 #14）**：上次没改干净。真正让面板"歪到一边"的不是面板比屏幕宽，而是
> `GuiVideoImport` 自己声明了一个 `private int width`（导出宽度，默认 480），把 `GuiScreen.width`
> 遮蔽了——`layout()` 和整块暗底一直按 480 算，1280 宽的界面上它落在 x=60，左边还露着没盖住的地面。
> 字段改名 `videoWidth` 之后 `this.width` 才是视口，详见第 14 节。

**二、帧率上限 30 → 120**：

- `VideoImportQueue.FPS_STEPS` = `6, 8, 10, 12, 15, 24, 30, 48, 60, 90, 120`；`submit()` 的钳位放到 120。
- `VideoClip` 读 `meta.json` 时原来钳在 60，这次一起放到 120 —— 不然 120fps 的包会被当 60fps 播，
  播放速度刚好一半，看起来像"导入时丢帧"。
- 代价写在界面上：帧数 = 时长 × 帧率，120fps 是 30fps 的四倍帧数、四倍体积。默认仍是 12fps，
  没动，因为广播器那块屏看不出 60 和 120 的区别，占的是磁盘。

### 14. 进度条可定位、右键/F 全屏、导入窗口居中（批次 #14）

**一、进度条"点了就弹回原位"**（`GuiVideoSeek`，右键大屏打开的那个定位窗口）

窗口画的是**本机那份方块实体**的播放头，而跳转要经服务端。原来一次点击只发一个包，
服务端确认要一个来回；这段空档里窗口只能画旧值，手柄就自己弹回原处——看上去像"没点中"。
三处一起改：

- **先写本地**：`applySeek()` 先调 `te.seekTo(ms)`（本地那份方块实体只是三个字段：播放头、锚点 tick、
  脏标记），再发包。画面与手柄立刻跟过去。
- **服务端回一发**：`VideoSeekMessage.Handler` 改完播放头后把 `screen.getUpdatePacket()` 直接发给发起者。
  区块更新本来也会走，但它是按"谁在看这个区块"路由的，晚一两 tick；这段时间正是"弹回"看起来发生的地方。
- **没有本机副本时不允许拖动**：没有片长就没有比例，点哪儿都只能跳到一个猜出来的时间，
  手柄永远画在最左边——那也是一种"弹回去"。现在 `overBar()` 在 `haveClip` 为假时直接拒绝，
  提示改成"只能用 +/- 按钮"。

顺带：窗口宽度改为按视口算（`max(264, min(384, 视口-16))`），按钮按列宽现算，拉窗口时重排。

**二、播放窗口里那条进度条也能拖了**

以前底部那条只是画出来的百分比，点上去什么都不发生、画面照旧往前走——玩家的描述同样是"拖了又弹回原位"。
现在左键按住拖、松手 `player.seekTo()`（同时挪画面和音轨，声音不会留在原地），拖动中时间码跟着手指走。
手柄画成 2 px 白条，明确"这是可以抓的"。

两个顺带的坑：`handleMouseInput` 不能写成 `while (Mouse.next())`——原版是每个鼠标事件调一次这个方法，
里面把队列抽干会把拖动过程中的移动事件吃掉，拖一下就断；右键则在这个方法里单独拦下来做全屏。

**三、右键 / F 全屏**（`client/video/VideoFullscreen`）

- **右键 = 全屏开关**：窗口里按右键进全屏，再按一次回窗口。放大的是当前这幅画面——
  接了屏（大屏展示）就是大屏，没接屏（本机播放）就是播放器。打开窗口这个手势仍然由方块决定：
  接屏 → 展示窗口，没屏 → 播放器窗口，所以"右键控制哪个全屏"在进入那一刻就定好了。
- **F 键同一条路**，不再直接调 `Minecraft.toggleFullscreen()`。原版那个方法有两个坑：
  ① 它按自己的 `fullscreen` 字段翻面，那个字段与 `Display.isFullscreen()` 可能不一致
  （启动参数、F11、驱动切换），一旦不一致，一次"进全屏"实际执行的是"退全屏"——
  这就是**"按 F 之后游戏框反而变小"**；② 退全屏时它回到启动尺寸（`tempDisplayWidth/Height`，
  通常 854×480），不是玩家刚才用的窗口大小。
- 现在以 `Display.isFullscreen()` 为准决定方向；进全屏前记下当前窗口尺寸，退出来按那个尺寸还原。
  打开播放窗口时**不主动改显示模式**（默认就是普通游戏窗口/小框），全屏是两个按键才发生的事。
- 关窗时排队还原到"看片之前"的显示状态与窗口尺寸（`restore(generation, mc)`，带代次，
  防止同一 tick 里又开了另一个播放窗口时迟到的还原把新状态当自己的）。

**四、导入窗口居中**

见第 13 节的更正：真因是字段遮蔽。改名之后 `layout()`、暗底 `drawRect(0,0,this.width,...)`、
滚轮命中测试用的都是视口宽，面板回到正中。

### 15. 长片截断 / 有声音没画面 / 全屏归属 / 设置项让位（批次 #15）

**一、4 分钟的片子转出来只剩 2 分钟、而且只有声音**

三个独立的成因叠在一起，逐个查出来：

- **播放端静默截断（真因）**：`VideoClip.MAX_FRAMES` 写死在 **20000**。4 分 23 秒的片子
  按 120fps 导入是 **31618 帧**，读的时候被切到 20000 —— 同一部片在游戏里报 **2:46**，
  而包里的 `audio.wav` 还是完整的 4:23。于是 2:46 之后画面没有帧了、声音还在响，
  看起来就是"只剩两分钟、有声音没画面"。现在上限放到 **500000**
  （120fps 也有 69 分钟余量，12fps 有 11 小时），它只用来挡坏包，不再冒充长度限制。
  截断发生在**读包**这一侧，所以已经转好的旧包不用重转：换上这个 jar，帧数就回来了
  （前提是当时 ffmpeg 确实解出了全部帧）。
- **音轨不跟随帧包**：导入时 `runAudio` 不带 `-t`，PCM 取的是整段源视频。现在按
  实际解出的 `frames / fps` 截断（实测：263.483 秒的片子导出 wav 正好 263.483 秒），
  音画一起结束。顺带把那条**固定 120 秒**的提取超时改成随时长放大 —— 长片的音轨
  不会因为超时被整条丢掉（丢掉之后包里就只剩画面，反向的同一个坑）。
- **播放头跑赢解码器**：缓存只有 6 帧。播放头按帧率换算出的帧号如果落在缓存之外，
  `showFrame` 什么都拿不到，而解码线程仍旧匀速往前挪 —— 一旦落后就再也追不回来，
  表现就是"有声音、画面一帧都没有"。现在缺帧时调 `catchUp`：落后超过整个缓冲
  就让解码器直接跳到播放头（400 ms 内只喊一次，否则每帧 seek 会把缓存清得更空）。
  实测这台机器 854×480 的 JPEG 解码 + 归一化约 **312 帧/秒**，120fps 本身撑得住；
  这条修的是慢机、高分辨率、以及一屋子屏同时解码的情况。
- **顺带**：ffmpeg 的输出以前没人读。管道缓冲只有 64 KB，长片 / 高帧率转换的告警
  足够把它填满，一填满 ffmpeg 就卡在 write 上 —— 进度条停在半路，看着像"转到一半停了"。
  现在开一个守护线程一路读掉，只留尾部用于失败原因（失败提示里会带上 ffmpeg 自己的
  最后一句话，不再只说"没能解出画面"）。

**二、全屏归谁**

- **没接大屏**：右键播放器 → 播放器窗口，右键 / F 进全屏（和上一批一样）。
- **接了屏**：右键播放器只开"展示"窗口，**这里不给全屏入口**，提示行直接写
  「全屏请右键大屏」。全屏从大屏按：右键大屏 → 定位窗口 →「**全屏观看**」，
  点一下就是满屏（`GuiVideoScreen.watch(...)` + `enterFullscreen()`），关窗仍回到
  进全屏之前的窗口尺寸。
- 判定是现算的 `canFullscreen()`：展示窗口看"是不是从大屏进来的"，本机播放窗口看
  "现在有没有屏"。遥控器中途接上 / 拆掉大屏，下一次按键就是新结论，不缓存。
  例外只有一种：接了屏但那块屏不在本机视野里（另一个维度、人走远了）—— 那边根本点不到，
  本机播放又不是重复的第二路声音，所以这时入口留在播放器窗口，否则玩家两边都按不出全屏。

**三、「强制限制返回」让位**

接上大屏以后，这一项在播放器设置窗口里**整个不画**（不是灰掉），窗口就地重排，
不用关窗重开；拆掉大屏它自己回来。没接屏时的行为与上一批一致（开 / 关、拦 ESC、
状态行）。理由是那个开关本来就只在没有大屏时成立，接屏后留一个按了没用的入口
比不画更容易让人误会。

### 16. 右键重排：右键即全屏、Shift + 右键开菜单；倍速不再音画不同步（批次 #16）

**一、两种右键，各管一件事**

| 位置 | 手势 | 结果 |
| --- | --- | --- |
| 大屏 | **普通右键** | 直接满屏（`watch(...)` + `enterFullscreen()`），不再经过菜单 |
| 大屏 | **Shift + 右键** | 菜单：进度条 / ±5s / ±30s / 暂停 / 回开头 / **尺寸·倍速** / 全屏观看 / 关闭 |
| 播放器（接了屏） | 普通右键 | **什么都不开**：不抢全屏、不开菜单、不动倍速与进度 |
| 播放器（没接屏） | 普通右键 | 本机播放窗口，右键 / F 进全屏（和以前一致） |
| 播放器 | Shift + 右键 | 播放器设置窗口（音量 / 退出限制），未变 |

- 以前"看片"要走三步：右键大屏 → 窗口里点「全屏观看」。中间那一步没有产出，却是最容易被
  误触的一步 —— 那块窗口里每一处都在动播放位置（进度条、±30s、回开头）。现在看片是一下。
- **尺寸 / 倍速**原本是"蹲下右键大屏"的独立手势，现在收进 Shift + 右键的菜单：一个方块上不再
  需要记两套组合键。`GuiVideoScreen.mirror()`（右键播放器开的只读展示窗口）随之删掉，
  看大屏只剩 `watch()` 一个入口 —— 接屏以后"右键播放器又能看片又能改桌面模式"这条路没了。

**二、倍速下的卡顿与音画不同步**

一次开 2x 就能看出来：画面一顿一顿，声音越拖越远。两个独立的成因：

- **声音根本不变速**：`Clip` 只会按文件自己的采样率播放，倍速只搬了时钟（`filmSeconds`），
  音轨还是 1x。2x 跑一分钟，声音就落在画面后面 30 秒，而且越拉越大。JRE 的 `Clip` 没有变速
  播放，硬做重采样就是另起一条音频链，不是这一批的范围；所以现在**非 1.00x 时把音轨整个扣住**，
  回到 1.00x 先把音轨对齐到画面所在的时间、再放开 —— 宁可没声音，也不要一段越拖越歪的声音。
  配置窗口的倍速行下面直接写清这件事（「非 1.00x：画面优先，音轨静音」）。
  实现上 `VideoAudio` 多一个 `speedMuted`，和「这一路该不该出声」（`muted`，由音源仲裁决定）
  分开记，两者互不影响。
- **画面卡顿是追帧在清缓存**：上一批的 `catchUp` 从渲染线程发 seek，而 seek 会清空整个帧缓存，
  400 毫秒限频 → 高倍速下"卡一下、跳一格、再卡一下"，每秒两三次。现在改成**渲染线程只公布
  播放头**（`wanted`），解码线程发现播放头跑出缓冲就自己丢帧追上去，只清掉过期帧
  （`removeIf(key -> key < from)`），缓存里还在播放头前面的帧照样有用。少的是中间帧，多的是
  连续画面 —— 倍速下本来就只能看到 1/2、1/3 的帧。

配置窗口的倍速行、提示行、交付文档都跟着改了措辞，不再出现"右键大屏 → 全屏观看"这种
已经过时的说法。

### 17. 墙上的画面为什么会发暗：光照贴图乘了一次（批次 #17）

**现象**：同一部片，在播放器（GUI 窗口）里亮度正常，贴到大屏上明显发灰；几乎所有片子都一样。

**结论**：不是转码、不是解码、不是纹理格式，是**世界渲染阶段的光照贴图**。

- 大屏的画面是一个 TESR 四边形，画在世界渲染阶段。这个阶段 unit 1 上还挂着光照贴图，
  而固定管线会拿"当前的光照坐标"去采样它。这块四边形用的是 `POSITION_TEX_COLOR`，
  **没有自己的光照坐标**，于是采到的是上一个画过的方块 / 实体留下的亮度值 ——
  房间暗，屏就暗；游戏「亮度」设置也会跟着掺一脚。
- 播放器窗口为什么正常：GUI 阶段只留 unit 0，`disableLightmap()` 早就把 unit 1 关了，
  乘算不成立。这也解释了"同一部片、两个地方、两种亮度"。
- 这也解释了为什么 `cecp` 那批控件都在自己按 `setLightmapTextureCoords(…, 240, 240)`：
  同一个坑，早就踩过一次。

**修复**：`PanelPainter.glass` 与 `PanelRender.glass` 在画面绘制前把光照坐标钉到 240
（Minecraft 的满亮，单位是光照贴图的 1/256），画完用 `lightX/lightY` 还原给下一个 TESR。
一块屏是灯，不是被房间照亮的板子 —— 顺带让所有监视器（DFC 屏、核弹屏、告警屏、坠落屏）
在暗处也不再发灰。

**排除项（都是量化过的，不是推测）**：

| 怀疑 | 怎么排的 | 结果 |
| --- | --- | --- |
| 导入转码掉亮度（`-q:v 4`、`scale=lanczos`） | 包内第 7201 帧 vs 源 MP4 同一时刻的 PNG：meanRGB (43.3,19.5,57.7) vs (42.9,19.8,56.8)、luma 30.96 vs 30.87 | 无损失 |
| 色彩范围 limited/full（16–235）错配 | 同上，直方图 p1/p50/p99 完全一致 | 无偏移 |
| AWT 缩放（`TYPE_INT_RGB` + 双线性）吃亮度 | 同上，且解码路径只有 `normalise()` 一次绘制 | 无损失 |
| 纹理上传格式（`GL_RGBA` / 无 sRGB / 无 mipmap） | 走的是 `TextureUtil`，与所有 GUI 纹理同一条路 | 无损失 |
| 混合与 alpha | 顶点 alpha 255、`color(1,1,1,1)`、玻璃面 alpha 1.0 | 无压暗 |
| 光影包色调映射 | 该实例 `mods` 里没有 OptiFine / Iris，`options.txt` 无 shaderPack | 不适用 |

**已验证**：2026-11-18 在游戏内看过 —— 大屏与 GUI 窗口并排同一部片，亮度一致；改游戏「亮度」不再牵动屏幕画面。
原来的三条判定口径（亮度设置联动、房间明暗联动、与 GUI 窗口并排对比）都走过了。

### 18. 删掉倍速、电视窗、开窗口不再夺走画面与声音（批次 #18）

**一、倍速整条链删掉**

不是藏起来，是删干净：`GuiVideoScreenConfig` 的那一行、`VideoScreenConfigMessage`
里的 float、`TileEntityVideoScreen` 的字段与 `applySpeed`、`VideoPlayer.setSpeed`
与 `alignAudioToSpeed`、`VideoAudio.speedMuted` 全部移除，连 NBT 键也一起去掉。
原因是它本来就只能是半成品：`Clip` 只会按文件自己的采样率播放，0.25x–3x 只能搬
时钟，音轨要么拖歪要么被扣住——"能加速但没声音"不值得留一个入口。现在片子永远
按自己的帧率放，画面和声音不会再有第二次不同步。

**二、右键大屏 = 屏正中的一台电视**

| 手势 | 结果 |
| --- | --- |
| 大屏 · 普通右键 | 屏正中开一台电视（外壳 / 边框 / 屏幕内圈 / 底座 / 电源灯），世界压暗但不盖掉 |
| 大屏 · **F** | 收掉外壳，画面铺满；再按 F 回到这台电视 |
| 大屏 · 右键（窗内） | 同上 |
| 大屏 · Shift + 右键 | 菜单（进度条 / ±秒 / 暂停 / 回开头 / 尺寸 / 全屏观看 / 关闭） |
| 大屏 · ESC | 退出，回到看片之前的桌面状态 |

- 屏幕比例按片子自己的宽高算：4:3 的片子里屏幕就是 4:3 的，外壳是给画面做的，
  不是给画布做的。窗口再小也保证一个能看的最小尺寸。
- **全屏状态由窗口自己记账**，不看桌面。很多人本来就全屏玩游戏：那时按 F 只是
  "把电视外壳收掉"，桌面模式一点都不动；再按 F 回到电视，也不会把全屏的游戏
  踢成 854×480 的小窗口（只有窗口真的切过桌面时，退出才把桌面还回去）。
- 菜单里的「全屏观看」保留，等于"开电视窗 + 已经按过一次 F"。

**三、方块介绍改对了**

`hbmzz.video_screen.tip1/2` 原来还写着"右键：播放定位""蹲下右键：宽度、高度、
倍速"。现在是"右键：屏正中开一台电视（F 全屏 / 再按 F 回到窗口）"与
"Shift + 右键：菜单（进度条 / ±5s / ±30s / 暂停 / 回开头 / 尺寸）"。

**四、开别的窗口不再弄丢画面和声音**

`VideoAudioPolicy` 以前有一条："除了大屏窗口，任何窗口一开，全场静音"。它防的是
"两块屏 + 一个窗口同时出声"，但代价是：看片时开个箱子、看一眼机器、打开定位菜单，
片子立刻哑掉；而按 ESC 进暂停菜单时画面还在、只是冻住，正好是玩家说的"这个还
不算没了，就是停住不动"。现在规则改成：

- 接管窗口（本机播放）有自己的解码器 → 只它出声，墙静音（防重复）；
- 电视窗 → 它镜像的那块墙出声；
- **其余任何窗口 / 没有窗口** → 最近的墙照常出声。

墙的解码器与时钟本来就不随窗口开关走（`VideoScreenPlayback` 按方块自己算），所以
开窗口期间画面继续走、声音继续响；只有 ESC 暂停菜单在单人游戏里把整个世界停住，
那才是"停止不动"。

## 四、已知限制

- **监视器画面现在恒定满亮**，不再随房间光照变暗：这是"屏是屏"的选择。若有人想要"暗处也暗一点"
  的氛围感，那要另做一条按环境光调制的通道，别把光照贴图放回来。
- **已进游戏逐项实测**（2026-11-18，维护者在实际客户端走过）：大屏四个朝向的画面、32×32 的铺格、
  电视窗的观感与 F 的手感、音量滑条、遥控器两步连接、定位后的音画对齐与拖动进度条、导入视频 ——
  全部通过，未发现需要回滚的问题。此前的"未进游戏验证"一条作废。
- 播放头按**世界 tick** 推算（20 tick/s），不是逐帧同步：跨客户端最多差一两个 tick 的取整，
  肉眼不可见，但不等于帧级严格。真正的逐帧一致需要每帧广播位置，代价不值得。
- 客户端每帧只在**偏差 > 0.35 秒**时重定位；这个阈值是为了不把解码缓冲区每秒清空好几次。
- 片尾不会自动循环也不会自动停止：片子播完停在最后一帧，位置读数到片长为止，
  要重放按「回开头」或扳一次拉杆。
- 世界内大屏在同一客户端最多同时解码 **4 路**（超出的大屏保持黑屏，重新扳一次拉杆可再试），
  目的是不让一屋子屏幕各开一条解码线程。
- 音量 200% 受系统混音器 1.0 上限约束，响度到顶即止，不会破音。
- 「强制限制返回」的"有没有大屏"读的是本机这份方块实体：播放器所在区块被卸载时沿用上一次的结论，
  所以极端情况下（边走远边拆大屏）限制状态要等区块重新加载才更新；画面本身这时也已经不在播了。
  接上大屏后这一项在设置窗口里不画（入口让位），不是被灰掉。
- F7 只在没有打开 GUI 时响应（原版按键状态在 GUI 内不更新）；窗口里有「刷新列表」按钮。
- 大屏没有音轨时就是静音播放，播放器音量对它无效。
- 帧率仍取包的 `fps`（整数）。播放速率固定 1x，不再有倍速入口。
- **播放端仍然只解图片帧**：mp4 / mkv / mov 这些要先转成帧包。区别是现在不用命令行——
  蹲下右键播放器 →「导入视频…」→ 选文件 → 转换，转身就出现在列表里（底层还是 ffmpeg）。
  命令行 `tools/video/pack.py` 仍然可用，适合批量。
- **手动进入的播放界面不受「强制限制返回」约束**：ESC 随时可退，那条限制只作用于红石触发的全屏接管。
- **站立右键会让大屏真的开始播**：那是世界状态，多人服务器上等于替所有人按下播放；停止仍归拉杆
  （或右键大屏用定位窗口暂停）。这是"右键 = 展示"这个手势的代价，写在这里而不是留给玩家自己发现。
- **大屏展示与音源仲裁已进游戏实测**：电视窗借的是屏的解码器，多屏同房间只留最近一块发声，
  窗口切换那一瞬间的听感与画面都在客户端上确认过；结论不再只靠代码与静态检查。
- **120fps 只解决"能放"，不解决"值得放"**：帧数按时长×帧率线性增长，一部 24 分钟 120fps 的片子
  是 30fps 的四倍文件体积和四倍解码压力；广播器同时解码上限是 4 路，档位挑高之后更容易撞到这条线。
- **导入窗口的居中已在批次 #14 改动因**（字段遮蔽），面板位置只由视口尺寸决定，并已在游戏内确认居中；
  若日后再显歪，先确认 jar 里 `GuiVideoImport` 有没有 `videoWidth` 这个字段名。
- **全屏切换的行为只在代码层与静态检查上验证**：`VideoFullscreen` 用的是 LWJGL 的 `Display` 与
  `Minecraft.resize`，没有在真实显示器上按过 F；如果某个驱动拒绝 `setDisplayMode`，窗口会停在原模式
  （异常被吞掉，不会把画面带走）。
- **拖动进度条时服务端每 180 ms 收一次跳转**（原有节流），所以拖得很细的时候画面是"跳着"跟的，
  松手那一下才落定；本机播放窗口的拖动是本地的，没有这条延迟。
- **同一块屏同时被窗口与视角看到时只有一路解码**（本来就是同一个 `VideoScreenPlayback` 实体），
  但"同时解码上限 4 路"仍然算这块屏一份；一屋子超过 4 块屏时，超出的屏让出窗口也无法显示。
- 播放界面按 F 切换的是**系统全屏**（整块显示器），不是"隐藏底部进度条"；退出播放会还原进入前的显示模式。
- **追帧 = 主动丢帧**：解码跟不上播放头时（慢机、大分辨率、一屋子屏同时解码），画面会跳过中间的帧去追时间轴，
  所以"名义 120fps 的片子实际看到多少帧"取决于本机解码力。这是"迟到不如丢掉"的取舍，不是故障。
- **接屏后的全屏只在代码层验证过**：`enterFullscreen()` 是在 `displayGuiScreen` 之后立刻切显示模式，
  依赖 `Minecraft.resize` 把界面尺寸跟上；驱动拒绝 `setDisplayMode` 时窗口会停在原模式（异常被吞掉，
  不会把画面带走）。这一条和"右键大屏 → 全屏观看"的手感仍要进游戏确认。
- 3.7.0 分支的四向开合门、自定义贴图系统、旧 mixin 与运行时 FFmpeg 管线没有并入。

## 七、每次交付的固定动作

1. 编译：`./gradlew build --offline`，确认 `build/libs/hbmzz-3.8.0.jar` 的 `mcmod.info` 版本是 3.8.0。
2. 检查：`python tools/checkall.py --fast`，再按改动范围补跑对应单测
   （视频改动跑 `tools/videocheck/run.sh`，注册表改动跑 `tools/regcheck/check.py`）。
   Java 单测需要 `JAVA_HOME` 指向 JDK 8；`linkercheck` / `cecpcheck` 需要 `FASTUTIL` 指向
   gradle 缓存里的 fastutil（本机缓存在 `E:\hbm\gradle-home`）。
3. 部署：`python tools/deploy.py`，旧 jar 自动归档到 `backupsmod\hbmzz-old-jars`。
4. 文档：在本文件「六、交付批次」追加一行，更新「一、当前交付批次」的提交与哈希，需要时补「四、已知限制」。
5. 公告：`tools/site/content.json` 的 `timeline` 与 `docs/changelog.html` 同步当前版本条目，然后
   `python tools/site/sync_site.py` 刷新数据层。
6. 汇报：向用户给出「模组 jar 路径 + 源码位置/提交 + 本次改了什么 + 验证结果 + 未验证项」五件事。
7. 口吻：公告、文档、汇报一律按「刚发布」写 —— 新鲜、及时、简洁，像内容刚上线；
   不写「之前提到」「待同步」「暂时」这类滞后或草稿感的话，也不写大段版本沿革。
