// 逐版变更

从 2.1.5 到 2.3.1

机器控制面板、节点图控制台与视频广播器的逐版改动。每条尽量讲清「原来怎样 / 现在怎样」，而不是一句「优化了体验」。

v3.8.0 最新

播放器右键就能看片，蹲下才是设置，播放界面 F 切全屏

  • 两种右键分工：对着视频播放器普通右键直接开播——放的是这台机器上存的片源 与音量，不经过任何菜单；蹲下右键才是编辑窗口（片源、广播目标、打开文件夹、刷新列表）， 音量与「强制限制返回」收进这个窗口里的「播放器设置」按钮。以前右键先弹菜单、想看片还得再点 「测试广播」，现在是反过来：想改才蹲下。
  • 播放界面按 F 切全屏：F 调的是系统全屏，再按一次回到窗口；界面底部常驻一行 F 全屏。退出播放会把进入前的显示模式原样还回去，不会把桌面留在全屏里。
  • 「刷新无效 / 装进去不生效」查清了：不是模组没装上——日志里 hbmzz@3.8.0 正常加载，问题是视频目录里躺着一个 .mp4，而视频库只认 名字.zip 与 名字/ 两种形状，它被静默忽略了，于是列表永远只有那两个 zip，看起来像按钮坏了。 现在库会把这个文件记下来，窗口与 F7 的回执直接点名：「跳过 1 个不支持的文件：xxx.mp4（需打包成 zip）」， 目录里的 README 也写了同一句话——这个模组读的是图片帧序列，1.12.2 的 JRE 没有 H.264 解码器。 另外 preInit 会打一行 HBMZZ 3.8.0 loaded from <jar 路径>， 下次"装了没反应"先看这行指向哪个文件。
  • FFmpeg 会自己下，不用再手动装：首次启动时如果 config/rsaudiofm/bin 里还没有可用的 ffmpeg，主菜单阶段会弹出「正在准备音频播放器」进度页——后台线程走代理下载 BtbN 的 win64 包（约 190 MB），支持 Range 就切 64 段并行、断了下次只补没下完的段， 不支持就退回单线程；下载完在本地解出 ffmpeg.exe 并用 .stamp 记住来源， 之后启动不再重复下载。这一版源码里这段逻辑是缺的（只剩"释放 jar 内资源"，而包里没有那个资源）， 现已按上一版补回；下载期间播放线程问 ffmpeg 只会得到"暂时没有"，不会跟着下第二遍。
  • 大屏的朝向一次算清，四个面都正着看。 画面画在方块表面这层没变，变的是几何来源：面板中心用 ConsoleRig.anchor 从控制器格推出来， 旋转用 yawOf(facing)，贴图 UV 用 panelUv()——它的 u 是反向的，因为玩家站在正面时 局部 +x 正好是他的左手。以前这三件事各算一遍，结果是北面看着正常、东西两面镜像、上下颠倒； 现在统一从 ConsoleRig 取，四个朝向一致。
  • 尺寸不再靠右键循环，改成配置窗口：蹲下右键大屏（点哪一格都行，边缘格会转给控制器）， 宽与高分开加减，各自 1–32 格；倍速 0.25x–3x，四分之一步进。窗口里没有停止键——停止仍然是拉杆的事， 一块屏不该有两个互相打架的开关。改大改小都会真的铺格 / 收格，只会动这面墙自己的格子。
  • 右键就能把片子拨到某一秒，所有人看到的是同一帧： 右键大屏打开「播放定位」——一条可拖动的进度条、+/-5s、+/-30s、回开头、暂停 / 继续； 窗口里的时间和状态每帧都从方块读，不是窗口自己记的数。定位请求发给服务端：服务器改的是 方块上的播放头，再回写给范围内所有客户端，所以按键的人、旁边站着的人、服务器另一头的人 都会跳到同一处；单机走的是同一条路（中间就是集成的那个服务端），两种模式不会分叉。 播放头是「基准时间 + 走时」而不是帧计数：拨到 23 秒就从 23 秒接着播，音轨一起跳； 暂停时画面定住、时间不走，继续时从原位接上。两头都夹边界——服务器只收 0–6 小时， 客户端再按自己手上那份片子夹一次，于是「-5 秒」不会变成负数，片尾之后也不会反复重定位。 拉杆关掉仍是回开头，和以前一样。
  • 新增大屏遥控器（video_remote）：16×16 的手持机贴图，深灰机身、顶部信号窗、 中间方向键、底部两枚按键。它是普通物品，不可放置、不绑任何点击放置行为，也不会弹「不能放置」。 作用只有一个：右键播放器把它对准，再右键大屏完成连接（两者相距上限 64 格）。原来那条借用监控数据线 接大屏的路子整个移除，数据线回到它本来的工作——仪表、堆芯、摄像头。
  • 拉杆按「有没有大屏」分成两种语义：播放器接上大屏之后，红石只开 / 停那面墙， 误触拉杆不会把任何人切进全屏；没接大屏时保持仓库原逻辑——上升沿直接全屏接管，是否限制中途返回按 「强制限制返回」的设置来（默认限制）。 大屏所在区块没加载时也不会偷偷降级成全屏，只会写一行「大屏不在已加载区域」。
  • 音量与「强制限制返回」都收在播放器的设置窗口里：蹲下右键播放器打开，一条 0–200% 的 音量滑条，加一个强制限制返回开关，默认开启。播放界面里没有它的按钮，也没有入口——能改它的 只有这个窗口。它只在没接大屏时生效：全屏接管期间按 ESC 只提示、不退出；一旦这台播放器接上了大屏， 它立刻不生效，退出归大屏和拉杆，画面上的相关提示也一起消失。反过来大屏被拆掉，限制自动回到生效状态。 窗口里会直接写出「当前已接大屏 · 本项不生效」或「当前未接大屏 · 本项生效中」，不用去猜。
  • 运行中就能换片：广播器窗口新增「打开视频文件夹」（直接叫系统文件管理器）与「刷新列表」， 另外加了一个没被占用的刷新键 F7，丢完 zip 按一下即可，不用退游戏。没用 F3+T——那是原版的重载资源包， 按一次会把所有模型重新烘焙。
  • 回退到仓库原实现：上一版那套「序列帧播放器」替代方案（VideoClip 的文件集/时间线、 playlist、desc.txt 分段、往返播放、悬浮观看窗、多屏共用解码）整个撤掉， 视频仍按仓库的「文件名 + fps + 帧号」读取。音乐也回到仓库原版：片头恢复静音， 片尾仍是仓库自带的 the-ending-of-melting.mp3；自制配乐与英文口播的脚本、成品一并移除。
  • 保留这一版已经交付的三件事：防爆窗帘、纪念挂画、DFC 监控屏几何缓存， 以及那处启动崩溃修复（rsaudio:blast_door 的注册名只设一次）。
  • 基线先说清：本版在 3.7.1（upstream master 快照，提交 26195b1）之上增量， 3.7.1 已有的修复一条没回退；3.7.0 是另一条分支，只移植了窗帘与挂画，没有整体覆盖。
  • 版本号固定 3.8.0：三处版本戳（build.gradle / mcmod.info / HBMZZ.VERSION）对齐，此后除非明确要求不再升版。逐次交付记录见 交付文档。
  • 验证与未验证：gradle 真实编译出包；regcheck 79 条（新加「遥控器要连的方块必须让出右键」 「服务器先夹再存定位」「客户端按片长再夹一次」「播放界面不得出现按钮」「限制只在大屏缺席时成立」 「广播包必须带播放器坐标」「蹲下开菜单 / 站立开播」「F 必须真的切全屏」「刷新必须点名被跳过的文件」「下载器还在」「启动时缺 ffmpeg 会去下」）、videocheck、linkercheck、rbmkcheck、termcheck、 cecpcheck、快速检查全绿。大屏的画面观感、倍速下的音画、32×32 的铺格手感、定位后的音画对齐 都还没进游戏看过。
v3.6.1

渲染换成本项目自己的实现，外观一处未改

  • 为什么动它：监控屏那套渲染最初参照了节枝的 JiezhiMod，2026-11-03 拿到了可按 GPL-3.0 使用的书面授权。授权能用，但让整个发布声明长期挂在一份「别人的代码」上不是办法，所以逐块重写， 把授权压缩成历史记录。
  • 几何重写（ConsoleModel）：改成「先收集部件表（后板、四条边框、四条阴影线、 四颗螺钉、状态条、吊装总成）→ 一次性变换 → 一张角点索引表发射六面」。原先每个盒子自带一个 transform lambda，加零件时漏掉倾斜或推距不会被发现；现在没有那条路可走。0.075 半厚、0.10 边框、0.012 缝、 吊架各段长度全部沿用——这些是这台机器的设计事实，改了就是改版型。
  • 画布上传管线重写（TerminalCanvas）：AWT 给的是 ARGB 整型，而小端机器上 0xAARRGGBB 的字节序恰好就是 BGRA——直接按 GL_BGRA 上传即可，不必每像素写四个字节； 尺寸不变时改走 glTexSubImage2D，边缘加 CLAMP。600×400 的超采样画布每帧少约 140 万次字节写入。
  • 新增 PanelPainter：两个渲染器本来各写一份「关消隐 / 开混合 / 绑纹理 / 归还图集」， 一处修好另一处还烂着。现在只有一份，且写明了两条踩过的规矩：进入前关消隐、绑之前把纹理单元复位。
  • 怎么证明外观没变：这台机器没有 Minecraft 实例，肉眼验证不可能，于是新增 tools/rigcheck——把 6 种面板尺寸 × 5 个倾角 × 通电/吊装共 121 组参数的全部顶点导成数字， 新旧实现逐位比对（17,521 行，零差异），再压成 121 行指纹入库。谁以后改了几何，这条会当场红； 反向验证过：改一个字符就 FAIL。
  • 授权链：节枝的授权书与私信截图继续保留，但覆盖范围缩小为 BlockDFCMonitor、BlockDFCMonitorPart、TileEntityDFCMonitor 的控制器 + 占位格结构，以及 ConsoleRig 的倾角与锚点数学。逐文件状态写在 NOTICE.md 的「重写记录」里。
  • 没验证到的部分：只有编译、几何指纹与离线检查。TESR 的绘制顺序、坠落动画的观感、 画布上传在真驱动上的行为，都没有进游戏看过。
v3.6.0

mp3 直接放，外加一处「点面板边缘会崩」的修复

  • 并入了 wzh3203 的 rsaudiofm。25 个文件、6,000 余行，位置在 com.rsaudio.formats。从此 config/rsaudio/audio 里不再只认 .ogg： mp3 与 flac 放进去就能在播放器列表里选到、放出来，别的格式还能靠 ffmpeg 转码。 LibraryInjector 负责把非 ogg 文件注入曲库，PlaybackManager 负责把解码后的 PCM 直接推给声卡。
  • 但 MixinBooter 那一层被拿掉了，这是本次改造的核心。原插件是独立模组、改不了宿主， 只能靠 Mixin 注入 ClientSoundPlayer 的播放入口，于是玩家必须额外装 MixinBooter （2.4 MB 的 coremod）。合并之后宿主代码就在同一枚 jar 里，那把钩子直接写进了播放器自己的五个方法 （play / stop / stopAll / preview / stopPreview）：直出接管时提前返回，false 就照原样走原版引擎。 两个 mixin 配置、加载器、以及那个第三方依赖一并删掉。
  • ffmpeg.exe 没有随包。他的 jar 是 41.6 MB，其中约 35 MB 就是这份 二进制；而它只服务「转码」这一条路。FfmpegFinder 本来就会按 config/rsaudiofm/bin → 游戏目录 → mods/ → PATH 的顺序找， 找不到只关掉转码、直出照常。所以这里只保留探测逻辑，要用转码的自己丢一份进去。
  • 四个解码库随仓库走，构建时嵌进 jar。JLayer（mp3 解码）、mp3spi（接进 Java Sound SPI）、tritonus-share（SPI 基类）、jflac，合计约 0.48 MB。踩到并修掉一个坑：mp3spi 与 jflac 各带一个 META-INF/services/javax.sound.sampled.spi.AudioFileReader，直接 zipTree 叠在一起会互相覆盖，只有一种格式能被认出来，而且不报错。 新加的 formatsServices 任务把描述符并成一份，stripDevCache 在 reobf 之后再把库与描述符一起塞进最终 jar。
  • 修掉一个运行期崩溃：AbstractMethodError，点 2×2 面板的三个填充格必踩。 填充板要「转发右键给原点格」，原来走 IPanelOrigin 接口。接口里这个方法叫 onBlockActivated，实现类里那个重写却被 reobf 改名成 func_180639_a—— 接口声明不是 Block 的子类，映射表里没有它，名字原样保留，于是 invokeinterface 找到的是一个没人实现的方法。现在转发点直接按 Block 类型调用（BlockGatePart 从第一天起就是这么写的），接口里也不再声明它。 3.1.0 起就在，静态检查与编译都看不见，只有真去点面板边缘才会撞上。
  • OST 三首现在带封面。mp3 走 ID3v2.3 的 APIC，ogg 走 Vorbis comment 的 METADATA_BLOCK_PICTURE，同一张 ost-cover-512.png（那张三根电平柱的 OST 标）。 顺带把标签统一了：之前 ogg 的 artist 是 Yang Sibo、站点 mp3 的 artist 是 HBMZZ，同一首歌在锁屏和下载后显示两个作者名。烧录脚本 tools/audio/burn_cover.py 现在是标签的唯一来源。
  • 体积与验证：主 jar 从 16,155,037 B 增到 17,054,958 B （约 16.3 MiB；解码库 0.48 MB + 三首的封面各约 0.13 MB）。编译器一次过，离线检查全绿； 这台机器依然没有 Minecraft 实例，mp3 能不能真的响、面板边缘还会不会崩，都没有真机验证过。
v3.5.2

先把「起不来」修掉，再修两种「方块的四个状态位」

  • 3.2.0 到 3.5.0 的 jar 在任何环境都开不了机。DfcBlastWatch.onServerStopped 挂着 @SubscribeEvent，参数却是 FMLServerStoppedEvent——它继承的是 FMLStateEvent，不是 Event。EventBus.register 会在参数类型校验时抛 IllegalArgumentException: ... takes a argument that is not an Event class，而这次 register 发生在 preInit，于是模组加载失败、客户端进不去，报错还指向注册那一行而不是出问题的方法。改成普通无参方法，由 HBMZZ.serverStopping 显式调用（那里本来就在给 HackRegistry 与 DfcAutoShutdown 收尾），行为不变。
  • 这个错为什么能活三个版本：它只在 游戏启动 时才会炸，编译、regcheck、checkall、站点审计全都看不见；而我们这台机器上根本没有 Minecraft 实例，从 3.2.0 起就没有真机验证过。现在 checkall 快速档加了一条：扫所有 @SubscribeEvent，参数是 FML*Event、无参数、或多于一个参数都算红。
  • 巨型管道：meta 越界。它原来的状态容器有六个布尔属性（64 态），getMetaFromState 返回 0..63。1.12.2 的方块状态编号是 blockId + (meta << 12)，读回时 getStateById 只取 meta & 15 —— meta 只有四位，63 会写进别的方块编号区间，存盘后读回来是另一块方块、另一种形状。与 wzh3203 的修复合并：状态容器只保留水平四向（16 态），纯竖直段用单一模型（mask 17），meta 只写 0..15 的序号，读回时再映射成旧掩码；64 个模型文件一个没删，只是取其中 16 个。
  • 控制台：变体键的顺序。ctrl_console 的 blockstate 按声明顺序写成 up,down,facing，而 BlockStateContainer 内部是 ImmutableSortedMap，查状态时拼出来的键按属性名字母序（down,facing,up）—— 16 条一条都对不上，整块是紫黑缺失模型，日志里不会有任何报错。同样来自 wzh3203 的修复。
  • 我们自己也犯了同一个错。3.2.0 的 dfc_blast_sensor 写成 facing=south,active=false，active 应该在前。现一并修正——这颗方块从 3.2.0 起就没显示过模型。
  • 为什么以前没被发现：「没有变体匹配」不是异常，模型烘焙器只会退到缺失模型；离线审计也只比对了「blockstate 文件在不在」，没比对键里的属性名字。
  • 新增 tools/statecheck，四条：① 变体键按属性名字母序；② 同一文件内所有变体的属性集一致；③ 每个变体指向的模型文件真的存在；④ 进 meta 的部分不超过 4 位——注意判据不是「状态数 ≤16」（原版楼梯 24 态、BlockRedstoneDelayer 64 态都合法），而是「getMetaFromState 能返回的值 ≤15」，状态多但 meta 收窄的会被列为正常。
  • 把旧代码放回去验证过：检查器在修复前报两条红（ctrl_console 的 16 条键序、BlockGiantPipe 的「64 态，meta 可达 63」），修复后四条全绿。checkall 快速档 4 → 5 项。
  • 他的另一条线没有并入：v3.3.0 里还有一套 14 种音频格式的播放管线（26 个文件 5,714 行，附带 ffmpeg 与 MixinBooter 依赖，jar 从 2.3 MB 变 41.6 MB）。那是一个功能，不是修复，等定了再动。
v3.5.0

DFC 自动停机、三秒环绕，还有一扇 26×26 的地板门

  • DFC 自动停机。监视屏绑定 DFC 后，潜行 + 右键切换开关（普通右键仍是终端）。开关跟着绑定走：换核心、解绑、核心消失超过 10 秒，一律自动关闭——一台屏若在换了核心之后还记得「开着」，它就会去冷却一台操作者从没为它授权的堆。
  • 四段时序。AURA：坍缩开始，核心周围持续蓝色粒子 + 每 40 tick 一次能量爆发，温度不动。RETRACT：剩余 60 秒，温度第一 tick 压到 50 °C，再在剩余窗口里线性降到 0 °C，同时蓝色粒子从 7 格半径一路收到 0.6 格。HOLD：0 °C 保持 5 秒，并尝试清除上游坍缩。DONE：等核心停止坍缩 10 秒后复位。

v3.2.0

DFC 一炸，它就输出红石：一枚爆炸传感器

  • 新方块 dfc_blast_sensor（DFC 爆炸传感器）。满方块、铁质，硬度 4.0、抗爆 90——它的用处就是在事故里活下来把信号送出去，比普通机器结实得多。正面是镜头、其余五面是钢板，放下时正面朝玩家；有信号时换成亮灯模型。输出是六面弱充能加强充能，贴哪面哪面通，不需要先铺一格红石粉。
  • 判定只在服务端做一次，写进一张按维度分组的表。装十块和装一块的代价几乎一样，而且十块说的是同一句话。每块传感器自己去找核心、自己算距离是不行的：炸的那一刻恰好有一块所在区块没加载，它就永远补不回那一 tick。
  • 认的是两条「已发生的事实」，不是猜温度跳变。拉控制棒、倒冷却液、黑客平板改字段，温度都会跳，那种启发式天天误报。这里认的是：① NTM 的核爆实体 EntityNukeExplosionMK3 在核心旁边入世（DFC 熔毁时由核心自己 spawn，实体入世是 Forge 事件，比轮询准且零开销）；② 任何爆炸把核心方块本身列进了破坏清单（给原版 TNT、别家模组、本模组核弹留的兜底，ExplosionEvent.Detonate 里查）。两条都先问一句「爆炸点附近真有 TileEntityCore 吗」，所以在基地另一头引爆一枚普通核弹不会把它点着。
  • 两个半径是两件事。coreRange（默认 12）判这次爆炸算不算 DFC 的；range（默认 512，同维度）判我在不在听得见的距离内。DFC 大厅和应急机房通常不在隔壁，所以后者是 512 而不是 32。
  • 信号是阶梯不是曲线：满格按住 holdTicks（默认 100 tick = 5 秒，强度 15），再逐级衰减 decayTicks（默认 200 tick = 10 秒，14 → 13 → … → 1，约 14 tick 掉一级），然后归零灭灯。一次事故共 15 秒，同维度再炸就重新计时，不叠加。写成阶梯而不是线性小数的原因很实际：红石只有十六级，连续函数会让每个接收端各自取整一次，而每处的取整未必一样。
  • 强度变化时才通知邻居。15 → 14 不会自己传出去——邻居只在旁边有方块变化时重新取样，不通知的话比较器会一直停在第一次读到的 15。按默认配置一次事故发十五次通知，不是两百次。
  • 记录是瞬态的，不写存档。写进 WorldSavedData 意味着存档里留一条过期记录，下次进游戏传感器会先莫名其妙输出一段信号——那不是「续上」，那是伪造一次事故。代价是区块没加载就等于没看见，要长期记录请接事故显示器（那是另一套，有历史也有存档）。
  • 没有做成 2×2 吊装屏。它不是给人看的，是给导线看的：信号只需要两根线，设备越小越容易塞进墙里、塞进防爆门旁边的检修槽里。
  • 新增 [dfcSensor] 配置七项：enabled / range / coreRange / anyBlast / holdTicks / decayTicks / strength。右键传感器只给读数（当前强度、上次爆炸的距离与时间差、来源），不改任何东西。

  • 核弹是长方形壳体（10/16 宽、9/16 高），全图只允许放一颗。这条不是配方成本，是存档规则：由挂在主世界 MapStorage 上的 NukeRegistry（WorldSavedData）强制。放第二颗时先被 canPlaceBlockAt 拒一次，再被物品的 onItemUse 拒一次并给出文字理由，而不是让方块先建出来再被拆掉。爆炸摧毁方块不走 breakBlock，所以查询时会顺手清理指向空气的失效登记；未加载的区块一律当作「还在」——宁可拒绝第二台，也不允许重复。

  • 八级代码：GREEN（正常运行）、YELLOW（发生小插曲）、ORANGE（小型暴乱）、RED（重大事故）、MED（堆芯融毁事故）、OMEGA（堆芯爆炸事故）、ALPHA（核弹事件）、DELTA（设施毁灭级事故）。RED 及以上视为警报。代码广播器右键升一级、潜行右键降一级，红石上升沿把当前预设广播出去；ALPHA 是唯一由系统自己升的——起爆程序一开始就升，爆炸时再升一次并带上当量与坐标。手动 raise 是无条件覆盖的，因为处理完事故的人必须能把 RED 压回 GREEN；自动源走的是「只升不降」那条阶梯。

一台能改写任意机器数值的平板，和它捅出来的三种屏幕

  • 新玩法：黑客入侵。核心是一件道具黑客平板，右键打开一个终端。输入指令就能直接改写全图任意一台机器的数值字段——反应堆的 heat、通量、控制棒插入量，储能、蒸汽，都在可写范围里。它不按按钮、不拉控制棒，也不经过机器自己的事件表，所以「温度该涨到哪」这条控制逻辑被整段绕过去了。这正是它存在的意义：常规玩法里你得靠控制棒把堆压住，而它直接改堆本身。
  • 作用范围是「你加载着的区块」，不是「附近的机器」。target 接受绝对坐标，也接受 ~ 相对写法；只要那个区块被加载、那个方块实体属于 com.hbm / 本模组，就能写。写入前有四道闸：类名必须以 com.hbm. / com.hbmzz. / com.rsaudio. 开头（带点，否则 com.hbmzz 会被 com.hbm 误匹配）、字段不能是 static 或 final、只接受 7 种原始数值类型、拒绝 NaN 与 Infinity。
  • 监测屏当场就能发现，而且不是靠猜。它不比较温度跳变——拉一根控制棒也是跳变，那种启发式会天天误报。屏读的是世界级的写入记录：谁把值直接写进了它正在看的那个坐标。这条记录跟着采样一起下发，所以方块正面、HUD、终端窗口、平板四处天然一致，不需要各写一套判定。
  • 状态一 · 连接节点断开（60 tick / 3 秒）。命中该屏绑定的堆芯坐标后立刻进入：整屏黑底，MONITOR → LINK → CORE 三个节点、断线与红叉，大字「连接节点断开」加 ERR 0x1F，18 格恢复进度条，红色闪烁。每次写入都重新计时——连着写十次，屏就一直断着。

v2.7.0

RBMK 不再是一个 tick 就没了

  • 原来怎样：过热到 maxHeat()，基座模组在一个 tick 内把整台堆变成废墟。行为正确，但它是发生在你身上，不是发生给你看 —— 上一秒还是一台在跑的机器，下一秒就是废墟，唯一的证据是你没来得及截的那张图。
  • 现在怎样：温度超过 1000° 且 ReaSim 蒸汽爆满时，控制棒开始上下跳动；跳满一分钟后整个顶盖被炸飞，翻着跟头升空约 25 格，落回堆芯时引发二次爆炸，再被掀飞一次（这次约 113 格），最后落地、冒烟，堆芯按基座模组自己的方式熔毁。
  • 跳动直接用诅咒版的。不是新画一套动画：诅咒版附属在 TileEntityRBMKBase 上加了 leafia$damage 字段，它的跳动、棒底喷流、落回时的撞击音全部由这个字段驱动。我们只负责决定要多少（一分钟内从 240 抬到 1150），把动画交给它 —— 两套动画叠在同一根棒上只会打起来。
  • 为什么停在 1150。那个字段到 1200 时附属自己会调 meltdown()。写超过去，堆会在我们的倒计时结束前被基座模组拆掉，顶盖永远不会飞 —— 一段看起来能跑、只在真堆上才失效的死代码。
  • 沸腾到爆炸之间，热量被按住了。这一个小时（一分钟）里每根柱子的 heat 被钉在 maxHeat()-50：不钉住，基座模组会在头几秒内走到自己的熔毁线，倒计时还没走完堆就没了。钉子由爆炸自己拔掉。
  • 顶盖是实体，不是方块。落地时把自己放回世界会在原地生成一根活的 RBMK 柱——一台从瓦砾里长出来、带方块实体、能继续运行的堆。所以 EntityRbmkLid 只是实体：带着原堆每根柱子的顶盖、按原样排布、按各自的 cover 贴图上色；落点不改写世界，只炸、只掉碎块。
  • 「蒸汽爆满」有两种判法，取并集。一是对着 maxSteam（16000）比；二是总量连续两次扫描不涨。后者是必须的：好几个整合包把容量改到 80000 而字段还是 16000，只看字段的话 20% 就判满，堆会在完全没到极限时炸掉。
  • 配置：rbmk.surge（总开关，关掉就是原来的一个 tick）、rbmk.heat（默认 1000）、rbmk.jumpTicks（默认 1200 = 一分钟）、rbmk.blastPower（默认 10）、rbmk.melt（顶盖落定后是否交给基座熔毁）。
  • 新增 tools/rbmkcheck（50 项）。熔毁是唯一没法「跑一遍看看」的功能——跑完存档就烧了。所以判断「什么时候开始、警告多久、哪些柱子是一台堆」的那一层被写成不含任何 Minecraft 类型的纯函数，50 项离线用例逐条验：一分钟倒计时不提前、跳幅单调且始终低于 1200、蒸汽只有一半满时不许触发、对角线不算相邻、相邻但不同高度不算一台、顶盖布局字符串往返不丢半格偏移。

  • 删掉了 6 格距离分簇。v2.6.0 用「同族零件相距 ≤ 6 格」判断哪些零件属于同一台反应堆。这个半径替玩家回答了一个玩家没问的问题：30 格宽的 DFC 会被判成好几台，锅炉装在隔壁房间的反应堆会被拆开，而两台碰巧贴着盖的堆又会被并成一台——三种情况都没法反驳。

一台反应堆就是一个部件类型

  • 新增：同一类别的机器折进同一个槽位。一台 RBMK 是十几个方块实体——燃料通道、控制棒、蒸汽发生器、吊车台。以前它们各占一个联动器标签，窗口里就是十几个标签、十几次 use；现在同族、同一台反应堆的零件只占一个槽位（RBMK），一个窗口调整台堆。
  • 归类是三级，全部自动：①部件类型看方块实体类名（含 RBMK → RBMK 反应堆，含 DFC → DFC 反应堆，储罐／炮塔／警报／门／电源盒／警示灯／控制台各自一族，表里没有的类各自成族，不合并）；②同一台反应堆按同族零件的切比雪夫距离 ≤ 6 格链式分簇，所以大堆仍是一簇、隔开的两台堆是两个槽（RBMK#2）；③部件名称是机器类型名（「RBMK 控制棒（手动）」），广播就认它。
  • 只在同族 ≥ 2 台时折叠。单独一台仍用它原来的标签（A、你起的名字），六台互不相干的机器那块面板和以前完全一样；没接机器的空槽也留在原位，标签条不会塌成「只剩接了线的几个」。
  • 读是整组，写是分流。read 的数值键给最小–最大（40/40/40/80 显示 40–80），文本键给不同取值；keys／events／变量名取并集；新增 parts 列点名册（有哪些名字、各几台）；set／ev 成功后回一行实际台数 ×4。
  • 新增：同名零件自动广播。任何一条写入——旋钮、面板规则、CE 节点图、终端——落到一台已绑定机器之后，会复制给同面板 + 同部件类型 + 同部件名称 + 同一台反应堆的伙伴，不跨机组、不跨族、不跨面板，单次上限 32 台。两个例外不扩散：部件类型槽位上发起的整组写入，以及节点图一次发往多个位置的广播——它们本来就是发给整组，再扩散会变成 N×N 次投递（瞬时按钮会被按两次）。
  • 钩子只有一个。MachineBridge.fire 改成转调 fireAll，广播挂在 fireAll 上：以后新增任何写入路径都不可能「忘记广播」，就像它不可能忘记发送事件本身。
  • 自检加 5 条（tools/regcheck，共 26 条）：fireAll 必须还挂着 PartBroadcast.fanOut；PartGroup.fire 与 ControlEventSystem.broadcastEvent 必须自己打开范围闸（否则 N×N 投递）；TerminalShell.execute 不许直接收裸 host（否则静默退回一标签一槽）；部件类型表必须还认得 RBMK 与 DFC。tools/termcheck 同时加了 14 条组用例（按名字计数、事件分流、只投递一次、parts、×N、聚合读数、无世界时不折叠），共 60 条。
  • 已知边界：两台贴着盖的反应堆会被认成一簇——它们之间没有超过 6 格的空地，几何上没有别的办法区分。真要分开，中间留 6 格以上的间隔。
v2.5.1

中文槽位名不再印成豆腐块

  • 修：终端输入行左边的提示符，槽位名是中文时变成一排空方框。自研面板的槽位是 A–F，提示符永远只有三个字母，所以这个位置一直用等宽字体画也没人发现；CE 控制台的槽位是你自己起的中文标签（反应堆），等宽字体没有汉字，AWT 就画它自己的「缺字」方框——不报错、不崩溃，只是看起来像坏了一样。
  • 根因不是漏了一个字体调用，而是「量宽度和画字各挑各的字体」。现在窗口里所有文字都走同一个入口：字体由要画的那个字符串决定（有汉字就用中文字体，纯 ASCII 才用等宽），量宽度、算光标位置、按像素裁剪用的是同一个函数。两边不可能再算出不同的宽度。
  • 顺带修掉同类的两处：DFC 监视器终端标题右侧的「· 核心名」，以及底部状态条变成「数据中断」时（那一条平时是纯 ASCII，只有断开时才带上汉字）。
  • 自检加 2 条（tools/regcheck，共 21 条）：终端窗口里不许再手工取等宽字体（字体必须由字符串决定）；build.gradle / mcmod.info / HBMZZ.VERSION 三处版本号必须一致。都做过回退验证。
  • 附带：日志里那句 Client attempting to join with ... hbmzz@2.0.0 终于是对的版本号了——HBMZZ.VERSION 是编译期常量，从 2.0.0 起就没跟着升过，五个版本的日志都在报旧号。现在由上面那条自检盯着。
v2.5.0

终端搬进 CE 控制台

  • 新增：CE 控制台的自定义控件列表里多了「终端」。就是那个从诅咒版移植过来的控制台：放一个终端控件，用联动器给它起名字绑上机器（名字就是槽位名），右键它打开命令窗口。原来终端只长在模组自己的控制面板上，这次按同一个用法搬到了移植面板里，而不是反过来给模组面板加功能。
  • 槽位不再只有 A–F。CE 控制台每个控件各有一套 taggedLinks，槽位就是你在联动器页签里起的那个名字。于是 use 后面可以写名字（带空格也行，例如 use RBMK 控制棒组），也可以写序号；ls 仍用 * 标当前目标。
  • 命令语言抽成与面板无关的一层。两块板子不共享任何一个类，所以补全与执行都写在一个 TerminalHost 接口上：动词、提示、错误文字只有一份。终端装在哪种面板上，语法都一样。
  • 目标选择跟着存档走。选中的槽位存进控件自己的 vars，随面板 NBT 一起保存；槽位顺序按标签名排序而不是联动器的插入顺序——那块 map 是从 HashMap 重建的，两次读档可能给出不同顺序，第 2 个槽位换台机器比没有槽位更糟。序号越界时退回第一个，而不是让四个槽位列着却一个都读不了。
  • Tab 补全不发包。服务端每次回包都带上槽位表，以及当前目标的可读键名、事件和变量名；客户端对着本地这份副本补全，一次按键零往返。执行仍然只在服务端——客户端只发一行文本和一个控件序号，服务器用自己的面板解析。
  • 限流：一个终端每秒最多 10 行，超了直接回「命令太频繁了」，免得一条命令刷爆机器的事件总线。
  • 自检加 3 条（tools/regcheck，共 19 条）：addon 控件类型必须有中文名（漏了就把英文键塞进中文菜单）；写出来的控件类必须真的进注册表（2.3.0 就是这么丢的物品和 TE）；注册名不得重复——重复在 put 时静默覆盖，面板照常加载，只是少了一个控件。三条都做过回退验证，确认会红。
  • tools/termcheck 换成新接口，并加一组 host 用例：按名字 / 前缀 / 字母解析槽位、带空格的 use、以及快照补全与 ls 的标记。
v2.4.2

控制台编辑器一开就崩

  • 修：控制台编辑器（CE 控制台）打开即崩。崩溃报告只显示 updateScreen 里的 ArrayDeque.getFirst()，真凶在两帧之前：ControlType 的类型表是静态初始化时一条条填的，而 addon 的 3 个类型要等某个类第一次碰到它们才登记；编辑器的类型菜单正好一边遍历这张表、一边通过注册表解析每个类型——解析就触发了那 3 条登记，等于往自己正在遍历的列表里追加，于是 ConcurrentModificationException 打断 initGui，元素栈没被填上，下一 tick 才崩在空栈上。
  • 类型表在启动时就补齐。注册表初始化时先强制登记 addon 的三个类型，之后再没有任何代码能改这张表。
  • 菜单遍历快照。类型列表改成 ControlType.all() 的副本，按钮 id 与点击时解析用的也是同一份快照——表后来变长也不会让按钮错位。
  • 编辑器不再被一个子菜单带走。元素栈先入栈再初始化子元素，所有取栈顶都改成可空；某个子元素 initGui 抛异常只记一条 ERROR，界面照常打开。一个 bug 不该以另一个更严重的面目出现。
  • 修：窗口缩放（F11 / 改 GUI 缩放）会让类型菜单里的按钮累积一份副本，越缩越多。
  • 新增自检 tools/cecpcheck（8 项）：断言「注册表 init 之后类型表就是完整的」，并在同一进程里按菜单的方式遍历一遍——修复前是 9 个类型、遍历中变 12 个。
  • regcheck 加两条：编辑器不得无保护地取空栈顶；类型表只能通过 all() 读，字段不得再变回 public。
